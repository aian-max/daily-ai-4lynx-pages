01Microsoft · 11월 2일 · AI 개발

코딩 에이전트가 빨라질수록 명세와 검증이 중요해진다

어떤 소식인가요? Microsoft의 Copilot Cowork 개발팀이 에이전트로 작업을 병렬화하며 얻은 교훈을 공유했습니다.
팀은 작업 범위, 성공 기준, 기존에 깨뜨리면 안 되는 동작을 명세에 먼저 적고 각 에이전트에 좁은 작업을 맡겼다고 설명합니다.

함께 볼 점 기사에서 소개한 대량의 PR 수는 Microsoft 사례의 측정치입니다. 건수 자체보다 테스트가 실제로 실패를 잡는지 확인하고, 중요한 변경은 사람이 검토하도록 한 점이 실무에 더 가깝습니다.

업무에 연결하면 먼저 작은 작업 하나에 ‘무엇을 바꾸는가·어떻게 검증하는가·무엇은 유지하는가’를 적어 보세요. AI가 낸 변경은 기존 리뷰와 테스트 절차를 거쳐야 합니다.

02Anthropic · 11월 2일 · Claude API

긴 대화의 요청량을 줄이는 message threads 베타

어떤 소식인가요? Anthropic은 Messages API에서 대화 상태를 서버에 보관하는 message threads 베타를 공개했습니다.
이후 요청에는 새 메시지만 보내는 방식으로 긴 대화나 에이전트 반복 작업의 요청 크기와 첫 토큰까지의 시간을 줄이는 것이 목적입니다.

함께 볼 점 스레드는 마지막 요청 5분 뒤 만료되며, 마지막 사용 후 최대 1시간 이내에 삭제된다고 안내합니다.
API 베타 기능이므로 일반 Claude 화면이나 사내 환경에 자동 적용된다는 뜻은 아닙니다.

업무에 연결하면 System Engineering이나 도구를 연동하는 팀은 긴 대화 이력을 매번 재전송하는 구조와 비교해 볼 수 있습니다. 도입 전 데이터 보관 조건, 인증, 비용과 SDK 지원 여부를 확인하세요.

03OpenAI · 11월 3일 · 엔지니어링

AI를 CAD·PCB 설계와 시뮬레이션에 적용한 사례

어떤 소식인가요? OpenAI가 ChatGPT와 Codex를 활용해 CAD 모델 수정, 제조 도면 작성, 시뮬레이션 준비를 돕는 사례를 소개했습니다. 자체 제작한 기기에서는 외장, PCB와 소프트웨어 설계까지 모델을 사용했다고 설명합니다.

함께 볼 점 회사가 직접 소개한 초기 사례입니다. 제조 준비 과정에서는 공차와 조립 조건 등을 충분히 반영하지 못해 여러 차례 사람의 검토와 수정이 필요했다고 밝혔습니다. 사례가 반도체 IP 설계의 정확성이나 검증 완료를 입증하는 것은 아닙니다.

업무에 연결하면 여러 문서에 흩어진 제약을 대조하거나 시뮬레이션 준비에 필요한 입력 목록을 정리하는 작업부터 살펴볼 수 있습니다. 회로 특성, 제조 조건과 최종 설계는 담당자와 검증 도구로 확인해야 합니다.

04OpenAI · 11월 2일 · AI 평가

일상 과제로 AI 성능을 살펴보는 LifeVal

어떤 소식인가요? OpenAI는 사람들이 일상에서 도움을 원하는 과제를 바탕으로 AI 모델을 평가하는 LifeVal을 소개했습니다.
육아, 교육, 가계 관리, 쇼핑과 공공서비스 이용처럼 실제 생활에서 마주하는 작업을 포함합니다.

함께 볼 점 공급자가 설계한 평가 결과는 모델 비교의 한 자료이지만, 회사의 설계·지원 업무에서 같은 성능을 보장하지는 않습니다. 과제 구성과 평가 방법을 함께 읽어야 합니다.

업무에 연결하면 우리 업무에서도 추상적인 모델 순위보다 실제로 반복하는 작업 몇 개를 정해 보고, 답변의 정확성과 확인 시간을 함께 비교해 보는 접근이 유용합니다.

05OpenAI · 11월 3일 · AI 평가

안전성 평가와 실제 사용 환경에서 달라지는 에이전트 행동

어떤 소식인가요? OpenAI 연구진은 AI 에이전트의 안전성 평가 결과가 비슷한 실제 사용 상황으로 얼마나 이어지는지 살펴봤습니다. 연구에서는 모델이 평가 목적을 어떻게 추정하는지가 행동 차이에 영향을 줄 가능성을 조사했습니다.

함께 볼 점 실험한 특정 모델과 안전성 과제에 관한 연구이며, 모든 업무에서 같은 차이가 난다는 뜻은 아닙니다. 평가 점수만으로 실제 환경에서의 안전한 동작을 단정하기 어렵다는 점에 주목할 만합니다.

업무에 연결하면 AI 도구를 시험할 때 정답이 분명한 예제뿐 아니라 실제 업무와 비슷한 문서·오류 상황도 별도로 점검해 보세요. 테스트를 통과해도 도구 권한과 결과 검토 절차는 유지해야 합니다.

기초

회의 메모를 실행할 일 목록으로 바꾸기

회의가 끝나면 결정된 내용과 해야 할 일이 메모 속에 섞여 있습니다. AI에게 요약만 요청하기보다, 누가 무엇을 언제까지 해야 하는지 별도로 뽑아 달라고 해보세요.

이렇게 요청해 보세요

아래 회의 메모에서 후속 조치를 추출해 주세요. 각 항목을 작업 내용 | 담당자 | 기한 | 관련 결정사항 | 확인할 점으로 정리해 주세요. 결정된 사항과 제안만 나온 사항을 구분하고, 담당자나 기한이 없으면 ‘확인 필요’로 표시해 주세요. 같은 작업은 합치되, 누가 맡을지 추측하지 마세요. [회의 메모]

결과를 확인할 때

원문에 없던 담당자와 날짜가 들어갔는지, 제안이 결정사항으로 바뀌지 않았는지 확인합니다. 확인한 목록은 담당자에게 공유하거나 다음 회의의 진행 현황 점검에 활용할 수 있습니다.

용어 정리

후속 조치
회의에서 정한 내용에 따라 담당자가 이어서 처리할 일입니다.
중급

인터페이스 명세에서 테스트 케이스 초안 만들기

새 기능의 검증을 시작할 때 정상 요청만 먼저 떠올리기 쉽습니다. 인터페이스 명세에서 요청과 응답의 조건을 뽑고, 경계 상황까지 테스트 항목으로 확장해 보겠습니다.

1. 명세에서 확인할 조건 뽑기

아래 인터페이스 명세를 읽고 요청 수락 조건, 응답 조건, 대기 중 동작, reset 동작을 정리해 주세요. 각 항목에 원문 근거를 붙이고 명세에서 확인할 수 없는 동작은 질문으로 남겨 주세요. [인터페이스 명세]

2. 테스트 케이스로 확장하기

정리한 조건을 바탕으로 테스트 케이스를 작성해 주세요. 각 케이스는 ID | 초기 조건 | 입력 순서 | 기대 결과 | 명세 근거로 정리해 주세요. 정상 요청 외에 연속 요청, 응답 대기, 요청 대기 중 reset도 검토해 주세요. 명세가 허용하거나 정의하지 않은 동작은 임의로 정하지 말고 확인 질문으로 표시해 주세요.

검토 포인트

예를 들어 backpressure가 허용되는 인터페이스라면 수신 준비가 되지 않은 동안 요청 신호와 데이터가 어떻게 유지돼야 하는지 명세와 대조합니다. AI가 추가한 기대 결과는 검증 담당자가 명세를 확인한 뒤 테스트 플랜에 반영합니다.

용어 정리

Backpressure
수신 측이 준비되지 않아 송신 측의 전송을 기다리게 하는 흐름 제어입니다.
Reset
회로를 정해진 초기 상태로 만드는 신호 또는 동작입니다.
중급

PVT 결과에서 규격에 가까운 조건 찾기

시뮬레이션 결과가 여러 corner에 걸쳐 있으면 규격을 벗어난 항목뿐 아니라 여유가 작은 조건도 함께 살펴야 합니다. 결과표와 규격을 함께 주고 비교표를 만들어 보겠습니다.

이렇게 요청해 보세요

아래 시뮬레이션 결과를 규격과 비교해 주세요. 항목 | process corner | 전압 | 온도 | 측정 조건 | 결과 | 규격 | 여유 또는 초과량 순서로 정리해 주세요. 상한 규격은 ‘상한 − 결과’, 하한 규격은 ‘결과 − 하한’으로 여유를 계산하고 음수인 경우 초과로 표시해 주세요. 단위나 비교 방향, 측정 조건이 불명확하면 판정하지 말고 ‘확인 필요’로 남겨 주세요. 표에 없는 고장 원인은 추측하지 마세요. [규격과 측정 조건] [corner별 결과]

결과를 확인할 때

AI가 계산한 여유는 원본 데이터와 계산식으로 다시 확인합니다. 같은 항목이라도 부하, 입력 조건이나 단위가 다르면 단순 비교하지 않습니다. 여유가 작은 조건은 파형과 해당 시뮬레이션 설정을 함께 살펴보세요.

용어 정리

PVT
공정(Process), 전압(Voltage), 온도(Temperature)를 묶어 부르는 말입니다.
Corner
공정·전압·온도 등의 특정 조합으로 정의한 분석 조건입니다.
중급

Bring-Up 로그로 다음 확인 순서 정하기

보드가 예상대로 부팅되지 않을 때 로그의 마지막 줄만 보면 앞 단계에서 이미 문제가 시작된 경우를 놓칠 수 있습니다. 기대 순서와 실제 로그를 나란히 놓고, 확인된 사실과 가설을 분리해 보겠습니다.

준비할 자료

기대하는 초기화 순서, 시간 정보가 포함된 로그, 확인 가능한 FW·보드 버전을 함께 준비합니다. 정상 동작 로그가 있다면 비교 자료로 추가합니다.

이렇게 요청해 보세요

아래 초기화 순서와 bring-up 로그를 비교해 주세요. 1. 로그로 성공을 확인할 수 있는 마지막 단계와 근거 2. 처음 이상이 나타난 시점과 관련 로그 3. 가능한 원인별 추가 확인 방법과 필요한 자료 를 정리해 주세요. 로그에서 확인한 사실과 가설은 분리하고, 보이지 않는 동작은 추측하지 마세요. 추가 확인은 상태 조회 등 영향이 작은 방법부터 제안해 주세요. 실제 보드 조작이나 설정 변경은 하지 마세요. [기대 초기화 순서와 버전] [로그] [정상 로그가 있다면 추가]

결과를 확인할 때

‘마지막 로그’가 곧 마지막 성공 단계라는 보장은 없습니다. 로그가 기록되지 않은 경로가 있는지 코드와 실제 보드 상태를 확인하고, 가설마다 레지스터 값이나 계측 결과 같은 추가 근거를 확보합니다.

용어 정리

Bring-Up
새 보드나 칩을 처음 동작시키며 전원, 클록, 펌웨어와 주요 기능을 단계적으로 확인하는 과정입니다.
FW
장치의 동작을 제어하는 펌웨어입니다.
중급

요청 메일에서 담당자와 처리 기한 뽑기

여러 메일에 구매 요청, 서류 제출, 일정 변경이 섞여 있으면 회신할 일과 실제 처리할 일을 놓치기 쉽습니다. 메일 내용을 한 번에 요약하기보다 요청과 진행 상태를 따로 정리해 보겠습니다.

1. 처리할 항목부터 정리하기

아래 메일에서 처리할 요청을 추출해 주세요. 요청 내용 | 요청자 | 담당자 | 기한 | 현재 상태 | 원문 근거 순서로 표를 만들어 주세요. 담당자와 기한이 명시되지 않았다면 ‘확인 필요’로 표시하고 추측하지 마세요. 이미 완료된 일과 아직 확인 중인 일을 구분해 주세요. [확인이 필요한 메일 내용]

2. 확인할 질문과 회신 초안 만들기

위 표에서 담당자나 일정이 불명확한 항목만 골라 확인 질문을 작성해 주세요. 각 질문에는 어떤 메일을 근거로 했는지 표시하고, 요청자에게 보낼 짧은 회신 초안도 작성해 주세요. 정해지지 않은 일정이나 처리 완료 여부는 만들지 마세요.

결과를 확인할 때

메일의 날짜가 회신 기한인지 실제 업무의 마감일인지 원문에서 구분합니다. 담당자와 완료 여부를 확인한 뒤 업무 목록에 옮기고, 회신은 내용을 검토한 후 보냅니다. 메일을 입력할 때는 사용하는 도구의 자료 취급 기준을 따릅니다.

용어 정리

후속 조치
요청을 처리하기 위해 담당자가 이어서 수행할 일입니다.
심화

병렬 에이전트 리뷰, 정말 도움이 되는지 비교하기

여러 에이전트에게 동시에 리뷰를 맡기면 시각은 늘어날 수 있습니다. 다만 같은 문제를 반복하거나, 작업을 나눈 탓에 전체 흐름을 놓칠 수도 있습니다.

이번에는 단독 리뷰와 병렬 리뷰를 같은 조건에서 비교해 보겠습니다.

준비할 것

작은 코드나 문서 한 건과 사람이 미리 확인한 점검 항목을 준비합니다. 자료 사용과 에이전트 권한을 확인하고, 각 세션은 읽기 전용으로 제한합니다. tmux처럼 여러 터미널 세션을 관리하는 도구를 사용해도 좋습니다.

비교 실험

  1. 에이전트 하나에 전체 리뷰를 맡기고 결과와 소요 시간을 기록합니다.
  2. 별도 세션 세 개에 요구사항 대조, 경계 조건, 근거 확인을 각각 맡깁니다. 결과가 서로 영향을 주지 않도록 독립적으로 진행합니다.
  3. 세 결과를 합쳐 중복 지적과 상충하는 의견을 표시하고, 실제 코드·문서로 근거를 확인합니다.
  4. 미리 정한 점검 항목의 발견 여부, 잘못된 지적, 중복, 소요 시간과 비용을 단독 리뷰와 비교합니다.

세션 하나에 줄 지시

담당 범위: 경계 조건을 검토합니다. 출력: 위치 | 관찰한 조건 | 문제가 생길 가능성 | 근거 | 추가 확인 사항 제약: 파일을 읽기만 하고 수정하거나 명령을 실행하지 마세요. 확인되지 않은 내용은 가정으로 표시하세요.

결과가 많다는 것만으로 품질이 높다고 판단하지 않습니다. 분할 때문에 전체 흐름의 오류를 놓치지 않았는지, 근거 없는 설명이 최종 결론에 섞이지 않았는지 사람이 확인합니다.
