RTL을 설명받을 때 동작과 근거를 분리하기

처음 보는 RTL을 AI에게 맡길 때는 ‘무슨 회로인지’만 묻기보다 신호의 갱신 조건과 코드 근거를 함께 요구해 보겠습니다.

그다음 reset과 enable이 겹치는 경우를 따로 질문하면 빠진 조건을 찾기 쉽습니다.

1. 신호와 조건부터 정리

다음 RTL을 보고 레지스터의 갱신 조건, reset 조건, 값 유지 조건을 표로 정리해 주세요. 각 설명 옆에 근거가 되는 코드를 표시하고, 코드만으로 알 수 없는 요구사항은 질문으로 남겨 주세요. [검토할 RTL]

2. 경계 조건을 다시 질문

reset과 enable이 동시에 활성화되면 어떤 동작이 우선하나요? 클록과 reset의 관계도 코드 근거를 들어 설명해 주세요.

답변은 코드 리뷰의 출발점입니다. reset 극성·비동기 여부와 조건의 우선순위는 원본 코드와 시뮬레이션에서 직접 확인하세요. 업무 코드를 입력할 때는 사용 중인 도구의 자료 취급 기준을 따릅니다.

용어 정리

RTL

회로를 정해진 초기 상태로 만드는 신호 또는 동작입니다.
기초

측정값을 비교할 때 조건부터 정리하기

측정값 두 개가 다르다고 해서 곧바로 회로 특성이 달라졌다고 판단할 수는 없습니다. 온도나 전압, 측정 방식이 달랐을 수 있기 때문입니다.

AI에게 값을 정리시킬 때는 비교 조건도 함께 남기도록 요청해 보세요.

연습해 보기

다음 숫자는 설명을 위한 예시입니다.

아래 데이터를 온도와 지연 시간으로 나눠 표로 정리해 주세요. 가장 큰 값과 작은 값을 각각 표시하되, 원인이나 합격 여부는 판단하지 마세요. 25°C: 82 ps / 85°C: 91 ps / -40°C: 77 ps

어디를 볼까요?

표에서 온도와 숫자가 짝을 유지하는지, 단위가 바뀌지 않았는지 확인합니다. 예시의 최대값은 91 ps, 최소값은 77 ps입니다. 실제 측정 결과를 비교할 때는 공정, 전압, 온도와 측정 조건을 함께 확인해야 합니다.

FW 초기화 경로를 나눠 읽고 다시 합치기

FW를 처음 볼 때는 클록 설정, 주변장치 초기화, 오류 처리 경로를 한 번에 파악하기 어렵습니다.

AI 에이전트 세 개에 서로 다른 범위를 읽게 하고, 마지막에 호출 순서와 빠진 부분을 합쳐 보겠습니다.

작업을 나누는 방법

  1. 사용이 허용된 프로젝트에서 읽기 전용 작업 범위를 정합니다.
  2. 세 세션에 각각 클록, 주변장치, 오류 처리 경로를 맡깁니다. 파일 경로와 함수 이름을 함께 보고하게 합니다.
  3. 각 결과를 모아 실제 진입 함수의 호출 순서와 대조하고, 충돌하는 설명을 다시 확인합니다.

주변장치 담당 세션에 넣을 질문

프로젝트를 읽기 전용으로 살펴보고 주변장치 초기화 경로를 찾아 주세요. 진입 함수 → 호출 함수 → 설정되는 주변장치 순서로 정리하고 각 항목에 파일 경로와 코드 근거를 붙여 주세요. 파일을 수정하거나 명령을 실행하지 말고, 코드만으로 확인되지 않는 순서는 추측하지 마세요.

병렬로 나눠 읽으면 함수 간 의존관계를 놓칠 수 있습니다. 마지막에는 실행 순서와 초기화 실패 시 동작을 코드와 실제 테스트 결과로 확인하세요.

용어 정리

FW
장치의 동작을 제어하는 펌웨어입니다.
AI 에이전트
목표에 따라 여러 단계를 수행하고 설정된 도구를 사용할 수 있는 AI 시스템입니다.
중급

공지문을 쓰기 전에 빠진 정보부터 찾기

공지 초안을 바로 쓰게 하면 날짜나 장소가 빠진 상태에서도 그럴듯한 문장이 나올 수 있습니다.

먼저 필요한 정보를 점검하고, 확인한 내용만 넣어 작성하는 두 단계로 나눠 보겠습니다.

1. 먼저 확인할 항목 찾기

사내 AI 교육을 공지하려고 합니다. 대상은 전 직원이고 일정은 11월 중입니다. 공지 전에 확인할 항목과 그 이유를 표로 정리해 주세요. 정해지지 않은 날짜나 장소는 만들지 마세요.

예를 들어 정확한 일시, 장소 또는 접속 방법, 신청 여부, 담당자 연락처가 빠졌는지 확인할 수 있습니다.

2. 확인한 정보로 초안 작성

확인한 내용만 사용해 직원용 공지 초안을 작성해 주세요. 아직 정해지지 않은 항목은 [확인 필요]로 남겨 주세요. [확인한 교육 정보]

보내기 전에는 일시와 참석 대상, 신청 방법을 담당자가 확인합니다. 문장이 매끄럽다는 이유만으로 사실 확인을 생략하지 않는 것이 핵심입니다.

심화

병렬 에이전트 리뷰, 정말 도움이 되는지 비교하기

여러 에이전트에게 동시에 리뷰를 맡기면 시각은 늘어날 수 있습니다. 다만 같은 문제를 반복하거나, 작업을 나눈 탓에 전체 흐름을 놓칠 수도 있습니다.

이번에는 단독 리뷰와 병렬 리뷰를 같은 조건에서 비교해 보겠습니다.

준비할 것

작은 코드나 문서 한 건과 사람이 미리 확인한 점검 항목을 준비합니다. 자료 사용과 에이전트 권한을 확인하고, 각 세션은 읽기 전용으로 제한합니다. tmux처럼 여러 터미널 세션을 관리하는 도구를 사용해도 좋습니다.

비교 실험

  1. 에이전트 하나에 전체 리뷰를 맡기고 결과와 소요 시간을 기록합니다.
  2. 별도 세션 세 개에 요구사항 대조, 경계 조건, 근거 확인을 각각 맡깁니다. 결과가 서로 영향을 주지 않도록 독립적으로 진행합니다.
  3. 세 결과를 합쳐 중복 지적과 상충하는 의견을 표시하고, 실제 코드·문서로 근거를 확인합니다.
  4. 미리 정한 점검 항목의 발견 여부, 잘못된 지적, 중복, 소요 시간과 비용을 단독 리뷰와 비교합니다.

세션 하나에 줄 지시

담당 범위: 경계 조건을 검토합니다. 출력: 위치 | 관찰한 조건 | 문제가 생길 가능성 | 근거 | 추가 확인 사항 제약: 파일을 읽기만 하고 수정하거나 명령을 실행하지 마세요. 확인되지 않은 내용은 가정으로 표시하세요.

결과가 많다는 것만으로 품질이 높다고 판단하지 않습니다. 분할 때문에 전체 흐름의 오류를 놓치지 않았는지, 근거 없는 설명이 최종 결론에 섞이지 않았는지 사람이 확인합니다.
