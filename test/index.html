기초

질문의 맥락을 주면
답변이 달라집니다

오늘은 AI를 처음 쓸 때 가장 먼저 익혀두면 좋은 방법을 살펴보겠습니다. 같은 주제를 묻더라도 듣는 사람과 사용 목적에 따라 필요한 설명은 달라집니다. AI에게도 그 배경을 알려주면 답변의 방향을 잡는 데 도움이 됩니다.

오늘의 핵심
대상 + 목적 + 요청할 작업 + 결과 형식 + 확인할 조건을 순서대로 적어보세요.

1. 먼저 막연한 질문을 살펴보세요

인터페이스 IP를 설명해 줘.

답변이 틀렸다는 뜻은 아닙니다. 다만 독자의 배경과 필요한 깊이를 알 수 없어, 전공자에게는 너무 쉽고 비전공자에게는 어려운 설명이 나올 수 있습니다.

2. 목적과 조건을 더해 다시 질문하세요

대상: 반도체 비전공 신입 직원 목적: 인터페이스 IP가 왜 필요한지 이해한다. 요청: 인터페이스 IP의 역할을 일상적인 비유 하나와 함께 설명해 줘. 형식: 5문장 이내. 전문 용어는 짧게 풀어 써 줘. 확인: 확실하지 않은 내용은 추측하지 말고 따로 표시해 줘.

3. 답변을 확인하고 한 번 더 다듬으세요

  1. 처음 요청한 대상이 이해할 수 있는 표현인지 확인합니다.
  2. 비유가 실제 기술을 잘못 설명하지 않는지 관련 담당자에게 확인합니다.
  3. 필요하면 “PHY와 컨트롤러의 역할을 구분해서 다시 설명해 줘”처럼 구체적으로 후속 질문합니다.

우리 팀 업무에 대입해 보면

Digital Engineering에서는 RTL을 놓고 신입 설계자에게 설명할 초안을 만들어 볼 수 있습니다. 예를 들어 “상태 전이 조건과 reset 동작을 나눠 설명해 줘”라고 범위를 정합니다. 실제 동작은 시뮬레이션 결과와 함께 확인합니다.

PHY Engineering에서는 측정표를 바탕으로 확인할 항목을 정리하거나, 예제 DRC 오류를 분류하는 질문을 만들 수 있습니다. 아날로그 회로와 레이아웃에 적용할 때는 실제 설계 규칙과 공정 조건을 승인된 자료에서 확인해야 합니다.

System Engineering에서는 FW 초기화 순서를 설명하거나, Chip Bring-Up 로그를 읽고 확인할 질문을 정리할 수 있습니다. 제안된 원인은 실제 로그와 측정 결과를 통해 검증합니다.

경영지원에서는 회의 안건으로 직원용 공지 초안을 만들고, 대상·일정·담당자가 빠지지 않았는지 점검할 수 있습니다.

기억해 둘 점: AI의 답변은 초안입니다. 기술적인 설명과 수치는 원문과 설계·검증 결과를 기준으로 확인하세요.

용어 정리

프롬프트 (Prompt)
AI에게 전달하는 질문이나 작업 지시입니다. 필요한 배경과 결과 형식을 함께 적을 수 있습니다.
RTL (Register Transfer Level)
디지털 회로의 레지스터와 그 사이의 데이터 흐름을 기술하는 방식입니다.
PHY (Physical Layer)
인터페이스에서 신호를 실제 물리 매체로 주고받는 계층 또는 관련 회로입니다.
DRC (Design Rule Check)
레이아웃이 공정에서 정한 설계 규칙을 만족하는지 검사하는 과정입니다.
FW · SW
FW는 펌웨어, SW는 소프트웨어를 뜻합니다.
Chip Bring-Up
제작된 칩을 처음 구동하면서 전원, 클록, 기본 기능 등을 단계적으로 확인하는 과정입니다.
PDK (Process Design Kit)
특정 반도체 공정에 맞는 설계·검증에 필요한 모델과 규칙 등을 담은 자료입니다.
중급

RTL을 읽을 때
동작과 근거를 함께 정리하기

처음 보는 RTL을 살펴볼 때 설명만 요청하면 reset이나 우선순위가 빠질 수 있습니다. 먼저 신호와 갱신 조건을 정리한 다음, 각 설명이 코드 어디에서 나왔는지 물어보겠습니다. 이때 AI의 설명은 리뷰의 출발점입니다.

1. 코드와 함께 질문하기

아래 RTL에서 q의 갱신 조건과 reset의 우선순위를 표로 정리해 주세요. 각 설명의 근거가 되는 코드도 함께 보여 주세요. always_ff @(posedge clk) begin if (reset) q <= 1'b0; else if (enable) q <= d; end

2. 한 번 더 좁혀 보기

방금 정리한 reset과 enable 조건이 동시에 참일 때 어떤 분기가 실행되는지 코드 근거와 함께 설명해 주세요. 요구사항이 없어 판단할 수 없는 부분은 질문으로 남겨 주세요.

확인할 점: 조건의 우선순위와 clock edge를 원본 RTL과 시뮬레이션으로 대조합니다. 업무 코드를 사용할 때는 사용 중인 AI 도구의 자료 취급 정책을 따릅니다.

용어 정리

RTL
레지스터와 데이터 흐름을 중심으로 회로를 기술하는 방식입니다.
Clock edge
순차 회로가 상태를 갱신하는 기준이 되는 클록의 전이 시점입니다.
기초

측정 결과를
읽기 쉬운 표로 바꾸기

측정값을 비교할 때는 숫자만큼 측정 조건이 중요합니다. AI에게 표를 요청할 때 온도와 단위를 함께 적고, 입력에 없는 기준을 임의로 채우지 않도록 지시해 보겠습니다.

질문 예시

아래 온도와 지연 시간을 표로 정리하고, 가장 큰 값과 가장 작은 값만 알려 주세요. 합격 기준이나 원인은 추측하지 마세요. 25°C: 82 ps / 85°C: 91 ps / -40°C: 77 ps

결과를 볼 때

세 값의 단위가 모두 ps로 유지됐는지, 온도와 값이 서로 바뀌지 않았는지 확인합니다. 이 예에서는 최댓값이 85°C의 91 ps, 최솟값이 -40°C의 77 ps입니다. 실제 실험에서는 공정·전압·온도 등 비교에 필요한 조건과 측정 방법도 함께 보아야 합니다.

용어 정리

PVT
공정(Process), 전압(Voltage), 온도(Temperature)를 묶어 부르는 말입니다.
ps
피코초로, 1조 분의 1초입니다.
고급

에이전트에 FW 초기화 분석을
병렬로 맡기기

처음 보는 FW를 살펴볼 때는 클록, 주변장치, 오류 처리 경로를 나눠 조사할 수 있습니다. 각 작업을 독립된 읽기 전용 에이전트 세션에 맡기고, 마지막에 근거가 겹치거나 충돌하는 부분을 확인합니다.

작업을 세 갈래로 나누기

  1. 예제 프로젝트와 에이전트 환경을 준비하고, 파일 변경·명령 실행·외부 연결 권한을 확인합니다.
  2. 세 세션에 각각 클록 설정, 주변장치 초기화, 오류 경로를 조사하게 합니다. 각 세션은 파일 경로와 코드 근거를 포함해 보고하도록 합니다.
  3. 결과를 한곳에 모으고 초기화 순서가 서로 충돌하는지, 호출 관계가 실제 코드와 일치하는지 확인합니다.
이 프로젝트에서 주변장치 초기화 경로만 읽기 전용으로 조사해 주세요. 진입 함수부터 호출 순서를 정리하고 각 단계의 파일 경로와 코드 근거를 표시하세요. 확인되지 않은 초기화 순서는 추측하지 마세요.

확인할 점: 병렬 분석은 순서와 의존관계를 놓칠 수 있습니다. 세션 결과를 실제 호출 흐름과 테스트 환경에서 교차 검증합니다. 터미널 멀티플렉서와 에이전트의 설치·접속 가능 여부는 환경에 따라 다릅니다.

용어 정리

FW
장치의 동작을 제어하는 펌웨어입니다.
에이전트
목표를 수행하기 위해 필요한 작업을 단계적으로 진행하고, 설정에 따라 도구를 사용하는 AI 시스템입니다.
중급

회의 공지에서
빠진 정보 먼저 찾기

공지문을 바로 작성하기 전에 AI에게 빠진 정보를 먼저 찾게 해 보겠습니다. 이후 확인된 정보만 사용해 초안을 만들면, 그럴듯하지만 잘못된 일정이나 장소가 들어갈 가능성을 줄일 수 있습니다.

1. 누락 확인

사내 교육을 공지하려고 합니다. 주제는 AI 기초, 대상은 전 직원, 일정은 11월 중입니다. 공지문 작성 전에 확인할 정보와 그 이유를 표로 정리해 주세요. 날짜나 장소를 지어내지 마세요.

2. 확인한 정보로 작성

확인된 정보만 사용해 직원 공지 초안을 작성해 주세요. 아직 미정인 항목은 [확인 필요]로 남기고, 제목·일시·장소·대상·준비 사항 순서로 정리해 주세요. [확인한 정보]

확인할 점: 참석 대상과 날짜, 신청 방법은 실제 담당자가 확인합니다.

주간 심화

병렬 AI 리뷰를 설계하고
단독 리뷰와 비교하기

여러 에이전트가 동시에 리뷰하면 관점이 늘어날 수 있지만, 같은 오류를 반복하거나 전체 맥락을 놓칠 수도 있습니다. 이번에는 코드 리뷰를 예로 들어 단독 리뷰와 병렬 리뷰의 결과를 비교하는 실험을 설계해 보겠습니다.

준비와 범위

작은 코드 예제와 사람이 미리 확인한 점검 항목을 준비합니다. 에이전트마다 동일한 입력과 접근 범위를 주고, 읽기 전용으로 실행합니다. 여러 터미널 세션을 관리할 때는 tmux 같은 터미널 멀티플렉서를 사용할 수 있습니다. 실제 에이전트 실행과 결과 검토는 별도로 설정해야 합니다.

실험 순서

  1. 기준선: 단일 에이전트에 전체 예제 리뷰를 요청하고 결과와 소요 시간, 도구 비용을 기록합니다.
  2. 병렬 분석: 독립된 세 세션에 각각 요구사항 대조, 경계 조건, 설명의 근거 확인을 맡깁니다. 서로의 결과를 보지 않도록 합니다.
  3. 통합: 결과를 중복 제거하고, 같은 주장에 대한 근거와 충돌을 표로 만듭니다. 불일치는 자동 결론 대신 사람의 검토 대상으로 남깁니다.
  4. 평가: 미리 정한 점검 항목 중 발견한 비율, 잘못 지적한 항목, 중복, 소요 시간과 비용을 비교합니다. 기준 자체가 불완전할 수 있으므로 신규 발견도 별도 검토합니다.
담당 범위: 경계 조건만 검토하세요. 출력: 위치 | 관찰한 조건 | 실제 위험 가능성 | 근거 | 확신 수준 제약: 파일을 읽기만 하고 수정하거나 명령을 실행하지 마세요. 확인되지 않은 문제는 가정으로 표시하세요.

실패를 살펴볼 지점: 세 리뷰가 같은 오류를 반복하는지, 분할 때문에 모듈 간 문제를 놓치는지, 근거가 없는 주장이 통합 과정에서 사실처럼 바뀌는지 확인합니다. 평가 결과가 좋지 않으면 작업 범위와 검증 기준을 바꿔 재실험합니다.

용어 정리

터미널 멀티플렉서
하나의 터미널 환경에서 여러 세션이나 화면을 관리하는 도구입니다. tmux가 한 예입니다.
기준선
새 접근의 결과를 비교하기 위해 먼저 측정한 기준입니다.
에이전트 (AI agent)
목표에 따라 작업을 단계적으로 진행하고 필요에 따라 도구를 사용하는 AI 시스템입니다.
