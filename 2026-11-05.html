OpenAI, 코드 리뷰 도구 업체 Pierre 인수 발표

함께 볼 점 이번 발표는 인수 계획과 개발 방향에 관한 것입니다. 현재 모든 사용자에게 새 기능이나 가격 변경이 적용됐다는 뜻은 아닙니다.

업무에 연결하면 에이전트가 여러 변경을 빠르게 만들수록 사람이 변경 범위와 근거를 살피는 화면이 중요해집니다. 우리 팀에서도 변경량보다 검토 가능성과 기존 테스트 통과 여부를 함께 확인해 보세요.

02OpenAI · 11월 2일 · 개발 인프라

병렬 코딩 작업에 맞춰 Git 백엔드 Pando 구축

어떤 소식인가요? OpenAI가 에이전트와 개발자의 병렬 작업으로 Git 요청이 늘어나자 자체 Git 백엔드 Pando를 구축한 과정을 공개했습니다. 기존 Git 프로토콜과 클라이언트를 유지하는 방향으로 설계했다고 설명합니다.

함께 볼 점 OpenAI의 대규모 저장소 사례입니다. 회사 측은 전환 후 중앙값 기준 push 지연이 약 80% 줄었다고 밝혔지만, 다른 저장소에서도 같은 개선이 난다는 뜻은 아닙니다. Pando의 외부 제공 계획도 아직 구체적으로 확정되지 않았습니다.

업무에 연결하면 여러 에이전트를 쓸 때는 코드 생성 속도만 보지 말고 브랜치 충돌, 테스트 대기, 리뷰 부담까지 기록해 병목이 어디에 있는지 확인해 보세요.

03Collinear AI · 11월 3일 · 보안 평가

코드 취약점 수정 능력을 평가하는 CWE-bench v2

어떤 소식인가요? Collinear AI가 AI 에이전트의 취약점 탐지·수정 능력을 살펴보는 CWE-bench v2의 공개 과제 100개를 소개했습니다. 실제 오픈소스 저장소를 대상으로 기존 기능을 유지하면서 취약점을 수정하는 방식입니다.

함께 볼 점 공개 과제에서의 점수는 해당 테스트 환경과 채점 방식에 한정됩니다. 데이터셋을 사용하기 전 접근 조건을 확인해야 하며, 보안 수정의 안전성이 순위만으로 보장되지는 않습니다.

업무에 연결하면 AI가 제안한 코드 수정은 취약점 해결 여부뿐 아니라 기존 기능이 계속 동작하는지도 테스트하세요. 기존 리뷰와 보안 절차를 함께 유지하는 것이 중요합니다.

04Google DeepMind · 11월 3일 · 연구 도구

문헌 조사부터 후보 분석까지, 화학 연구에 에이전트 활용

어떤 소식인가요? Google DeepMind가 Antigravity의 화학 연구용 기능을 활용해 문헌에서 화합물 자료를 모으고 분석·후보 설계를 지원하는 사례를 공개했습니다. 에이전트가 출처를 정리하고 연구자가 결과를 살피는 흐름입니다.

함께 볼 점 회사 측의 연구 시연이며, 예측으로 나온 후보는 실제 합성과 실험 검증이 필요하다고 명시합니다. 특정 연구 조건의 결과를 다른 분야에 그대로 일반화할 수는 없습니다.

업무에 연결하면 분야는 다르지만 문서 수집 → 조건 정리 → 후보 도출 → 전문가 검증이라는 분업 방식은 설계 자료나 측정 결과를 검토할 때도 참고할 수 있습니다.

05Anthropic · 11월 3일 · Claude API

일부 Claude 생성 텍스트에 워터마크 적용 안내

어떤 소식인가요? Anthropic은 일부 Claude 모델의 생성 텍스트에 텍스트 워터마크가 적용된다고 플랫폼 릴리스 노트에서 안내했습니다. 적용 대상은 모델과 이용 플랫폼에 따라 다릅니다.

함께 볼 점 공식 안내에는 일부 모델과 설정에서 워터마크가 적용되지 않을 수 있다는 예외가 있습니다. 워터마크 유무만으로 모든 문장의 출처나 사실 여부를 확정할 수는 없습니다.

업무에 연결하면 AI가 작성한 문서를 공유할 때는 작성 방식보다 근거 자료와 수치가 맞는지 먼저 확인하세요. 기능의 실제 적용 범위는 사용하는 모델과 플랫폼 문서를 확인해야 합니다.

기초

요청 메일에서 빠진 정보를 먼저 확인하기

요청을 받았는데 일정이나 결과물의 범위가 빠져 있으면 일을 시작한 뒤 다시 확인해야 합니다. 회신부터 쓰기 전에 AI에게 빠진 조건을 찾아 달라고 해보세요.

이렇게 요청해 보세요

아래 업무 요청 메일을 읽고 요청받은 일과 이미 정해진 조건을 먼저 정리해 주세요. 업무를 시작하거나 완료하는 데 필요한 정보 중 빠진 항목을 찾고, 각 항목에 확인이 필요한 이유를 한 줄로 적어 주세요. 날짜, 담당자, 결과물 형식이 없으면 임의로 채우지 말아 주세요. 마지막으로 요청자에게 보낼 확인 질문을 중요도 순으로 세 개 작성해 주세요. [요청 메일]

결과를 확인할 때

요청자가 이미 적어 둔 조건을 빠진 항목으로 잘못 분류하지 않았는지 원문과 대조합니다. 질문을 고른 뒤 실제 상황에 맞게 고쳐 회신하세요. 사내 자료를 입력할 때는 사용하는 도구의 자료 취급 기준을 따릅니다.

용어 정리

결과물
업무를 마친 뒤 전달해야 하는 문서, 표, 코드 등의 산출물입니다.
고급

시뮬레이션 로그에서 첫 실패와 후속 오류 분리하기

긴 regression 로그의 마지막 요약만 보면 처음 실패한 assertion이나 환경 오류가 가려질 수 있습니다. 에이전트에게 로그를 읽게 하되, 발생 순서와 원문 근거를 함께 남기도록 하겠습니다.

이렇게 요청해 보세요

이 디렉터리의 시뮬레이션 로그를 읽기 전용으로 확인해 주세요. 각 실행에 대해 테스트 이름, seed, 첫 ERROR 또는 FATAL의 시간과 원문, assertion 실패 위치, 종료 상태를 표로 정리해 주세요. 그 뒤 같은 실행에서 이어진 오류를 시간순으로 나열하되 선행 오류의 결과라는 인과관계는 확인되지 않으면 가설로 표시해 주세요. 파일을 수정하거나 시뮬레이션을 다시 실행하지 마세요. 로그만으로 확인할 수 없는 내용은 별도 질문으로 남겨 주세요. [로그 디렉터리 경로]

결과를 확인할 때

첫 ERROR가 실제 원인인지, 테스트벤치가 의도적으로 출력한 메시지인지 확인합니다. seed·테스트 이름을 원문과 대조하고, 필요한 경우 담당자가 같은 설정으로 재현해 파형과 assertion을 확인합니다. 도구 사용 권한을 먼저 확인하세요.

이렇게 요청해 보세요

아래 DRC 보고서에서 rule 이름, 위반 건수, cell 또는 계층, 위치 정보를 추출해 주세요. 같은 rule과 계층에 속하는 항목을 묶고 각 묶음에 원문 예시를 하나씩 붙여 주세요. 좌표나 단위가 없는 경우는 ‘확인 필요’로 두고, rule 설명에 없는 수정 방법은 만들어 내지 마세요. 마지막으로 layout 담당자가 원본 뷰어에서 확인할 질문을 세 개 제안해 주세요. [DRC 보고서]

결과를 확인할 때

동일한 rule이더라도 원인이 같다고 단정하지 않습니다. rule 정의와 좌표를 DRC 뷰어에서 확인하고, 제안된 수정이 다른 rule이나 회로 요구에 영향을 주는지도 검토합니다. 변경 후에는 승인된 flow로 재검증합니다.

이렇게 요청해 보세요

이 프로젝트에서 [진입 함수]를 출발점으로 FW 초기화 호출 경로를 읽기 전용으로 추적해 주세요. 호출 순서 | 함수 | 파일 경로와 줄 번호 | 수행하는 설정 | 실패 시 처리 순서로 표를 작성해 주세요. 조건부 컴파일, 런타임 분기, 인터럽트 때문에 순서를 하나로 확정할 수 없는 경우 조건을 함께 적어 주세요. 코드를 수정하거나 빌드·보드 명령을 실행하지 말고, 간접 호출이나 외부 라이브러리로 확인할 수 없는 부분은 표시해 주세요. [프로젝트 경로와 진입 함수]

결과를 확인할 때
